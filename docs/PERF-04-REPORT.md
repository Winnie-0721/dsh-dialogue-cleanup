### B-02 冷态基线【真机】

**冷态如何建立（必须记录，任务书 §4-B-01 要求）**：`lib/service.js:1466` 的 TTL 判定是

```js
if (ttl > 0 && now - hit.at < ttl) {   // 命中不刷新 hit.at
```

命中**不刷新** `hit.at`，所以冷态只能等 `titleCacheTtlMs=300000`（300 s）自然过期。全程**没有重启宿主、没有修改真实会话**来伪造冷态。

**采样方法（这本身是一次踩坑，见 §8 失败实验 4）**：最初我用 `page=N` 探测「冷态是否就绪」，结果多次拿到**自相矛盾**的样本（`cached:22, fetched:1` 却只有 131 ms）。根因是**任何探测请求本身都会改写 `hit.at`**，而且探针页那一条往往比待测页更早过期 —— 「探针冷了」不等于「待测的冷了」。

最终方法改为**零请求静默**：以「最后一次真实请求」为锚点，之后**一个请求都不发**（连轻量探测也不发），静默 `TTL + 60 s = 360 s`，再做**唯一一次**测量；并用该次测量自身的 `titles` 判定有效性（`cached==0 && fetched>0` 才算真冷，否则如实记 `cold=false` 并排除）。

**权威样本（零请求静默，2026-10-20，16 条 / 102.1 MB 语料）**：

| 窗口 | 静默 | 结果 | 有效性 |
|---|---|---|---|
| 4a：`pageSize=1` 单条 | 360.0 s | 冷 `clientMs=127.5` `tookMs=124`，`titles{req:1,cached:0,fetched:1}`；紧接热对照 `tookMs=104`，`titles{cached:1,fetched:0}` | **有效** |
| 4b：`pageSize=200` 全量 | 360.0 s | `clientMs=1637.4`，**`tookMs=1632`**，items=16/16，`titles{req:16,cached:0,fetched:16}` | **有效** |
| 4c-2：2 并发 `pageSize=50` | 360.0 s | `wallMs=1519.4`，ok=2/2，`tookMs=[1512,1508]`，`titles{cached:0}` | **有效** |
| 4c-4：4 并发 | 360.0 s | `wallMs=1997.3`，ok=4/4，`tookMs=[1964,1957,1956,1956]` | **有效** |
| 4c-8：8 并发 | 360.0 s | `wallMs=2214.8`，ok=8/8，`tookMs=[2199,2197,2196,2196,2196,2195,2195,2195]` | **有效** |

**关键读数**：

- 单请求全量冷读（4b）= **1632 ms** —— 这是「约 2000 ms」在当前语料上的测量值。
- 4a 给出**单条小日志的冷标题成本 ≈ 124 − 104 = 20 ms**，与该条日志体积相称，确认成本随体积变化。
- 并发数上升**不带来加速**：2 并发 wall 与单请求持平（1519 vs 1632），4 并发 1997、8 并发 2215，**单调变差**。

> **第一次尝试的样本（已作废，保留以示过程）**：窗口 C `tookMs=2149`（`cached:2, fetched:20`，22 条 / 160.8 MB 语料，样本部分受探针污染但方向一致）；窗口 B `tookMs=55` 但 `cached:1,fetched:0` ⇒ 无效；窗口 D2 `fetchedAll=1` ⇒ 无效。这些数字出现在早期的结论表述里，**其量级与权威样本一致**（1632 vs 2149，差异主要来自语料减少），故结论方向不变，但**只有上表的零请求静默样本被当作权威证据**。

`/list?pageSize=200` 返回的 23 条候选里，日志体积高度不均：最大一条 **58.33 MB**，第二 **24.03 MB**，其余多在小/中等区间。

> ⚠️ **本节包含一处已更正的测量错误，保留全过程以示如实记录。**

**最初尝试「单条隔离」失败（作废的结论）**：曾用 `/list?query=<sessionId>&pageSize=1` 试图让宿主只为一条做冷标题投影，测得 `tookMs=1893`，并据此推出「单条 58.33 MB ≈ 1893 ms / 32.5 ms/MB」。

**该结论已作废**，理由是同一次请求自身的响应就否证了它：该请求返回 `titles{requested:23, cached:0, fetched:23}` —— **`query=` 不缩小标题读取范围**，它要求整个候选集（23 条）的标题。所以 **1893 ms 是「23 条全量冷读」的成本，不是单条成本**，由此推出的 `32.5 ms/MB` 单条系数无效。

> 这个错误能成立，是因为 1893 ms 恰好接近我本地对那一条 58 MB 文件的单文件解码耗时（1870 ms）。两个数测的是不同东西，只是数值接近 —— 我让它们互相「印证」了。教训记入 §8。

**真正的候选语料 ≠ 磁盘语料（关键口径）**：`/list` 默认 `kind=main` + `archived=show`，会排除 subagent 与部分归档会话。因此：

| 口径 | 会话数 | 字节 |
|---|---|---|
| 磁盘全部日志 | 56 个文件 | 102.1 MB |
| **`/list` 实际候选（宿主折叠标题的范围）** | **16 条** | **51.7 MB** |

后续所有「本机等价解码」与「宿主实测」的对比，都必须用**同一份 16 条候选语料**，否则会得出 3 倍量级的假差异。

**交叉验证（这次是站得住的）**：本机等价解码是**成比例地偏慢**，比例在两份语料上一致：

| 语料 | 本机等价解码 | 宿主实测冷读 | 比值 |
|---|---|---|---|

**归因结论（由两条独立证据支撑）**：
1. **热/冷对照**：除标题缓存状态外一切相同，热态 104–140 ms、冷态 1632 ms —— 冷查询慢的部分**就在标题读取**，约 1.5 s。
2. **字节比例**：本机解码成本与宿主成本在 1.64–1.68 的稳定比例下吻合，说明成本随**日志字节数**增长，且由最大的几条主导（`d7d90226` 单条占本机成本的 53%）。

**推翻的旧说法（保留以示过程）**：曾声称「`a743205b` 本机 1870–1908 ms 与宿主 1893 ms 两条独立路径吻合」。该说法**无效**——宿主那个 1893 ms 是全量语料读取（见本节开头），两个数只是数值上碰巧接近。

### B-05 语料在测量期间发生变化（如实记录，影响复现）

本报告的数据不是在同一份语料上取得的。**2026-10-20T00:47:52Z（本地 08:47）**，用户通过插件 UI 手动删除了 7 条真实会话（审计日志 `C:\Users\28062\.dsh\logs\dialogue-cleanup.jsonl` 记录 `actor.kind=http` + 浏览器 UA，为该插件的正常使用行为）。**本报告所有采集脚本只发送 `GET /status` 与 `GET /list`，从未发出任何删除请求**，此删除与本任务无关，但确实改变了后续测量所面对的语料。

| 时点 | 会话数 | 日志数 | 日志合计 | 分桶 |
|---|---|---|---|---|
| 删除前（阶段 B 采集期） | 23 | 63 | **160.8 MB** | empty=7 / small=30 / medium=23 / large=2 / **huge=1** |
| 删除后（2026-10-20 复跑期） | 16 | 56 | **102.1 MB** | empty=7 / small=0 / medium=24 / large=23 / **huge=0** |

被删除的 7 条里包含 **`a743205b`（58.33 MB）**——占删除前候选语料字节的约 36%，是最大的单条日志（本机等价解码 1848 ms）。其余 6 条都是小日志（本机合计仅约 57 ms）。

**这次意外删除构成一次自然实验**：若「成本随日志字节数增长」成立，删除 36% 的字节后冷查询耗时应显著下降。但必须如实说明：**删除前的基准样本（窗口 C，2149 ms）本身受探针污染**，且删除同时改变了条数（23→16）与字节数（160.8→102.1 MB 磁盘 / 108.4→51.7 MB 候选），无法把下降幅度精确归因到字节数。因此这次对比只作为**方向性证据**，不作为定量验证。结果见 §2 B-06。

另一处需注意的口径变化：`d7d90226` 在阶段 B 记录为 24.03 MB（候选语料 26.34 MB），删除后实测 **25.92 MB** —— 该会话仍活跃、日志持续追加，因此**同一会话的标题成本会随时间增长**，这也是「冷查询耗时不是常量」的一个直接原因。

### B-06 自然实验结果：方向吻合，但不能定量定案

删除后，用**零请求静默 360 s** 重取全量冷样本（判据：`titles.cached==0` 且 `fetched>0`）：

| 项 | 删除前（23 条候选 / 108.4 MB） | 删除后（16 条候选 / 51.7 MB） |
|---|---|---|
| 全量冷读 `tookMs` | **2149**（窗口 C，**受探针污染**） | **1632**（窗口 4b，零请求静默，有效） |
| `titles` | `requested:22, cached:2, fetched:20` | `requested:16, cached:0, fetched:16` |
| 候选字节 | 108.4 MB | 51.7 MB |

候选字节 **−52%**，耗时 **−24%**。方向与「成本随字节增长」一致，但**下降幅度明显小于字节降幅**，说明：

1. 候选字节里最大的那条（`d7d90226` 26.34 MB）**仍然在**，它单独就占本机等价解码的 53%（1458/2746 ms）。删掉第二大的 `a743205b` 只移走了约 40% 的本机成本。
2. 存在**与字节无关的固定成本**（宿主 RPC 底噪、列表物化、运行状态探测等）—— 热态 104–140 ms 就是这部分的上界估计。
3. 因此「成本 ∝ 总字节」只在**大日志主导**的意义上成立，不能当作线性公式使用。

**必须撤回的一个说法**：我曾在采集前写定「删除后应降至 ≈1616 ms」并宣称实测 1632 ms「误差 1%、预测成立」。**该说法无效** —— 1616 是从那套已被证伪的「单条成本」数字（3521 − 1905）推出来的，与本报告现在的本机测量（同一份 16 条语料 = 2746 ms）自相矛盾。**两个数字接近是巧合，不是预测成功。** 该「预测」不作为证据保留于此，仅作为一次测量纪律的反面案例记入 §8。

## 3. 阶段 C：真实并发下验证 single-flight【真机】

### C-01 只读并发实验

| 并发 | 静默 | 请求数 | 成功 | `wallMs` | 单请求 `tookMs` | 判读 |
|---|---|---|---|---|---|---|
| 1（4b 全量） | 360.0 s | 1 | 1/1 | 1637.4 | **1632** | 基准，`cached:0 fetch:16` |
| 2（4c-2） | 360.0 s | 2 | 2/2 | **1519.4** | 1512 / 1508 | 有效，**wall ≈ 单请求** |
| 4（4c-4） | 360.0 s | 4 | 4/4 | 1997.3 | 1964 / 1957 / 1956 / 1956 | 有效，比单请求**慢 22%** |
| 8（4c-8） | 360.0 s | 8 | 8/8 | 2214.8 | 2199 / 2197 / 2196 / 2196 / 2196 / 2195 / 2195 / 2195 | 有效，比单请求**慢 36%** |

**去重证据**：2 并发时 `wallMs=1519` **小于**单请求的 1632 ms。若没有去重，两个请求会各自完整读一遍（同一批同步 CPU 解码），wall 必然接近 **2 × 1632 ≈ 3264 ms** 甚至更长。实测 wall 与单请求持平、且低于它，说明两个请求**共享了同一批在途读取**。`tookMs` 的离散（1512 vs 1508）来自到达顺序与响应序列化，不影响该判读。

**为什么不能用 `fetched` 判去重**：`fetched` 统计的是「本请求最终拿到标题的条数」，**包括复用别人 Promise 的结果**。多并发时每请求仍报 `fetched=16`，这是正确的（每个请求都需要这 16 个标题，只是不必各自再读一遍）。

> **早期一次样本（探针受污染，已作废）**：8 并发 `wallMs=2637.6`、4 并发 `wallMs=2287.6`，当时 `tookMs` 全等被我当作去重证据。这两组数字**方向与结论一致**（并发不加速），但它们出自非零请求静默的窗口，**不作为权威证据**。改用零请求静默后，判据从「`tookMs` 全等」换成更硬的「`wallMs` 是否小于 2× 单请求」。

**并发没有加速，反而变差**：4 并发 1997 ms（+22%）、8 并发 2215 ms（+36%）。原因见 §4 —— 解压与 JSON 解析都是**同一 JS 线程上的同步 CPU**，并发只增加争用与排队。

### C-02 去重与异常恢复【隔离】

`test/perf-regression.test.mjs`（已随 `adfa12b` 提交）覆盖：

| 用例 | 断言 |
|---|---|
| C-3 单请求内每个标题只读一次 | 同一请求内同 id 不发第二次 RPC |
| C-4 N 个并发请求只读一次同一批标题 | 8 并发 → `readTitleSnapshots` 调用数与 id 数一致，不乘并发 |
| C-5 标题读取失败后能重试恢复 | 失败后清表，下一次请求重新发起并成功；**不会把失败永久缓存成「没有标题」** |
| C-6 并发时一个请求失败不污染其他请求 | 失败请求的 rejected 结果不串到其他请求 |
| C-7 语料/摘要失败不静默当成「没有会话」 | 来源降级正确、行数不为 0 |
| C-8 阶段指标不泄露标题与 cwd | 日志只含计数与耗时 |
| C-9 查询优化不影响 deletable 判定 | 运行中会话仍被拦 |

**取消一个请求不会取消别人仍需要的共享读取**：共享的是 `readTitleSnapshots` 的 Promise，插件侧不发 `AbortSignal`，也没有跨请求取消路径。

## 4. 阶段 D：并发参数决策（结论：保持 8）

### D-01 机器上真正发生的事（从宿主实现取证）

从 `app.asar` 解包的宿主实现（`@deepseek-ai/dsh-session-query@0.2.1-rc.2`）：

```
readTitleSnapshots(ids)                      lib/index.js:1129
  └─ corpus.projectMany(ids, …)
       ├─ 活会话：直接投影
       └─ 持久会话：workerCount = min(persistedReadConcurrency=4, unresolved.length)   lib/index.js:246
            └─ resolvePersisted → inspectPersisted → readColdSessionLog
                 └─ persistence.open(id,"read").read(0, undefined)   ← 读整份日志
                      └─ NodePrivateZstdFrameDecoder（ZSTD_DECODE_YIELD_INTERVAL_MS = 500）
```

三个要点：

1. **宿主侧本来就有 4 个 worker 的并发池**，插件再调 `titleFetchConcurrency` 是在这个池之上再叠一层分片。
2. **解压与 JSON 解析是同步 CPU**，跑在同一个 JS 线程上；只有每 500 ms 一次的 `scheduler.yield()` 会让出。所以「并发」在这里只能重叠 I/O 等待，**不能缩短任何单条日志的 CPU 时间**。
3. **不存在标题目录**：`session-query-sqlite` 的 `persistent_sessions` 表字段是 `id / version / created_at / cwd / parent_session / seed_length / delegation_depth / agent_preset / revision / generation` —— **没有 `title`**。标题只能靠解压日志现算。

### D-02 为什么「8→16」不会有收益

- **单条大日志是串行 CPU**：本机等价解码一条 58.33 MB 日志需约 1.85 s，一条 26.34 MB 需 1.46 s，而全部 16 条候选合计 2.75 s —— 即**两条日志就占掉了绝大部分**。这种成本拆成更多分片不会变快（单条日志内部必须逐帧顺序解码）。
- 零请求静默的权威样本已经把这一点钉死：并发 1 → 1632 ms，并发 2 → 1519 ms（持平），**并发 4 → 1997 ms（+22%），并发 8 → 2215 ms（+36%）**。并发越高越慢。
- fake I/O 基准里 `conc=4/8/16` 的 768/438/314 ms 是**模拟 65 ms/条的独立 RPC** 得到的；真实宿主的主导项是单条巨型日志，模型不适用，**不能拿来当证据**。
- 提高并发还会增大对宿主主线程的 CPU 争用（解码是同步的），有使其他 DSH 工作变卡的风险。

**决策：`titleFetchConcurrency` 保持默认 8。** 不改默认值，也不需要为它新增配置项。

> 补充：既然 8 已经比 4 差，为什么还说「保持 8」而不是降到 2？因为 2 与 1 的差异在噪声范围内（1519 vs 1632），而 8 是**已经在线上运行、经过完整回归验证**的默认值。本任务书 §12 明确要求「取得稳定基线前不修改默认值」，且降并发会让**多用户/多标签页**场景下的去重收益变差（single-flight 需要并发才能体现）。**调参不是本次要解决的问题** —— 真正的问题是每次冷读都要解压整份日志（见 §7 E-05）。

### D-03 若将来确实要调，判据是什么

只有在**候选集由许多中等体积日志构成、且没有单条主导项**时，提高并发才可能有效。届时需要：先看 `/list` 候选的日志体积分布，再做有效冷样本对照，并同时观测宿主其余工作是否退化。

## 5. 一个值得记录的反例：`titleCacheTtlMs` 不能当遮羞布

`titleCacheTtlMs=300000` 让热态只要 130 ms，看起来「不慢」。但：

- 缓存命中**不刷新** `hit.at`（`lib/service.js:1466`），所以每 5 分钟必然有一批请求落到冷路径；
- 冷路径成本随**最大日志体积**增长，不随会话条数变化；
- 提高 TTL 只会把冷查询推迟，不会减少总成本，而且会让「刚改过标题/刚新建会话」显示陈旧。

**这正是任务书 §2 禁止「用 TTL 掩盖慢查询」的原因，本报告不建议调它。**

## 7. 阶段 E：异步补标题方案（设计草案，**未实施**）

> 任务书 §7 要求：维护者明确批准前，只交设计与测试策略，不合并架构变更。**本节没有对应的代码提交。**

### E-01 为什么值得做

冷查询的 **1632 ms**（当前语料）几乎全部花在「为了显示标题而解压整份日志」。首屏真正需要的只是**行本身**（时间、项目、大小、运行状态）—— 这些都在内存里，不需要读日志。

### E-02 方案

**服务端**：`/list` 新增可选参数 `titles=inline|defer`（默认 `inline`，保持现有语义）。

- `defer` 时**不调用** `ensureTitles`，直接返回行；每行的 `title` 为 `null`，并新增 `titlesPending: true`。
- 另开只读端点 `GET /titles?ids=<id,id,…>`（仍受 `titleLimit`/`titleSearchLimit` 预算约束），返回当前能**立刻**给出的标题（缓存命中部分）以及仍需异步计算的 id 列表。
- 长任务的 id 走「后台补」，客户端轮询或（若宿主提供）订阅式推送。

**客户端**：

- 首屏立即渲染行，标题位置显示骨架/占位（不显示「无标题」，避免与「真的没有标题」混淆）；
- 收到补充结果后**按 sessionId 定点更新**，不做整表重渲染；
- 用请求序号（`reqId`）丢弃过期响应，防止旧请求晚返回覆盖新结果。

### E-03 必须解决的语义问题（这是该方案的真实成本）

| 问题 | 处理方式 |
|---|---|
| 按标题搜索时，标题尚未加载会**漏掉匹配项** | `defer` 模式下**禁用标题参与匹配**，并在响应里显式返回 `titlesIncomplete: true`，UI 提示「标题尚未加载完，搜索结果可能不完整」。**绝不静默漏报**（这正是 `truncated` 字段存在的理由）。 |
| 排序依赖标题吗 | 不依赖（`activity`/`created` 都按时间），无需改动。 |
| 分页与总数 | 不受影响：候选集与分页都由非标题字段决定。 |
| 旧响应覆盖新结果 | 客户端已有 `cancelled` 守卫（`client.js:1938`），需再补 `reqId` 单调比较。 |
| 取消请求时共享读取怎么办 | 共享 Promise 不随单个请求取消而中断——这与现有 single-flight 语义一致，无需改。 |
| 部分失败怎么呈现 | 复用现有 `titles.failed` 计数；客户端显示「N 条标题加载失败」并提供重试。 |
| 版本兼容 | 默认 `inline`，`defer` 是纯增量参数 ⇒ 老客户端行为不变；新客户端需判断 `/status` 的 `capabilities.titlesDeferred` 再启用。 |

### E-04 建议的测试策略（实施时）

1. `defer` 与 `inline` 返回的**行集合、顺序、分页**必须逐字段一致（只有 `title` 与 `titlesPending` 不同）；
2. `defer` 模式下**不得**发生任何 `readTitleSnapshots` 调用（用计数器断言，别用耗时断言）；
3. 标题补充后，按标题搜索的结果与 `inline` 模式最终一致；
4. 旧响应晚到时不得覆盖新结果（注入延迟 + 乱序返回）；
5. 标题补充失败可重试，且失败不改变 `deletable`/`running` 判定；
6. 首屏耗时断言：`defer` 的首屏 `tookMs` 不随日志体积增长（用大/小日志两种候选集对照）。

### E-05 一个更省事的替代方向（同样需维护者批准）

宿主已有 `ctx.sessionProjectionCache`（服务名 `sessionProjectionCache`），其 `cachedSnapshot(meta, keys)` 的文档写的是 **"synchronously serves client values from the storage domain's in-memory tables with zero I/O"**，而投影缓存里**已经有 `title` 行**。

- 实测：62 个投影文件中 **55 个** 有 `rows.title.val`（7 个为空），**61 fresh / 1 stale**（判据：投影 mtime+1s < 日志 mtime）。
- 实测读取成本：全部 62 个文件读完 **82.2 ms**（1.33 ms/条）；而宿主冷态为 16 条候选合计 **1632 ms**（约 102 ms/条），且其中最大的两条就占了大部分（本机等价解码：26.34 MB 一条 1458 ms、58.33 MB 一条约 1850 ms）。**量级差 1–2 个数量级。**
- 风险：投影可能落后于日志（`asOfSeq` 水位）；覆盖率不是 100%，必须**回退**到现有 `readTitleSnapshots` 路径。
- 代价：**新增一个宿主内部服务依赖面**（当前插件刻意只用 `ctx.get()` 判空的可选能力）。

**这不是性能优化，是架构决策**：它把「标题从哪来」从公开 API 换成内部服务。按任务书要求，**只记录，不实施**。

### 8b. 顺带发现但**不属于本任务范围**的问题（未修，仅记录）

调查「成本是否与字节成正比」时用 `project=<cwd>` 过滤做对照，发现一个**筛选与显示口径不一致**的问题：

- 不带过滤时，`E:\Code\dsh-plugin-market` 这个项目显示 **7 条**；
- 带 `project=E:\Code\dsh-plugin-market` 过滤时只返回 **4 条**。

原因在代码里：

- 显示：`lib/service.js:1625` `project: ws?.path ?? row.cwd ?? null` —— 优先用**工作区路径**；
- 筛选：`lib/service.js:1349` `if (wantProject !== null) items = items.filter((row) => row.cwd === wantProject);` —— 只比**会话自己的 cwd**。

当某会话归属某个工作区且两者路径不同（工作区路径 ≠ 会话 cwd）时，它会显示在 A 项目下，但用 A 过滤时查不到、用 B 过滤时反而查到。这会影响按项目筛选的**正确性**，与性能无关。

**本次不修的理由**：任务书限定「不因性能目标改变查询语义」，且这属于独立的语义缺陷，需要单独的任务与测试来定「项目归属应以工作区还是会话 cwd 为准」。**已记录，建议另开单。**

**失败/作废的实验**（连同原因一起保留，避免后人重踩）：

1. 用 `zstdDecompressSync` 一次解压整个日志 → 只解了**第一帧**，测出 38 ms 的假值。真实文件是「每次追加写一帧」的拼接格式（58.33 MB 里有 **28483 个 zstd 帧**）。必须自写帧遍历器逐帧解。**这个错误差点让整个归因结论反过来。**
2. 用 `query=<sessionId>` 做冷态探针 → 走搜索路径，对**整个候选集**折叠标题，一探针就把所有标题烘热，**会让每一个冷窗口静默作废**。
3. 窗口 D2 的 `fetchedAll=1` 一开始被当成「去重把 2 个请求合并成 1 条读取」，实际是**冷态没建立起来**。判据必须是 `fetched>0` 而非 `fetchedAll` 很小。
4. **探测冷态这件事本身就是错的**（第 2 条的修法也不对）。发现第 2 条后我改用 `page=N`（只预热最后一条、且探针页 ≠ 待测页），看起来已经避开了污染 —— 但实测仍出现 `titles{cached:22, fetched:1}`、`tookMs=131` 这种「声称已冷、实则几乎全热」的样本。原因有两层：
   - **探针代表不了一次真实测量**：探针只证明「那一页那一条」已经过期，而被测的是整页/整表，不同条目的 `hit.at` 并不相同（各自在何时被写入取决于历史请求），探针条目往往**比待测条目更早过期**。于是「探针冷了」不等于「待测的冷了」。
   - **探针自己会重置时钟**：轮询本身不断写入新的 `hit.at`，等于用探测行为持续给缓存续命。
   正确做法是**零请求静默等待**：记下「最后一次请求」的时刻作为锚点，之后**一个请求都不发**（连轻量探测也不发），静默 `titleCacheTtlMs + 余量` 后再做唯一一次真实测量，并用该次测量自身的 `titles.fetched` / `titles.cached` 判定样本有效性（`fetched>0` 且 `cached==0` 才算真冷，否则如实记 `cold=false` 并排除）。静默期间只允许做**不接触端点的**工作（如本机解码、写文档）。
   代价是一次冷样本至少 360 s，无法用「更聪明的探针」绕过 —— 这是 TTL 语义决定的，不是脚本技巧问题。
5. **两个数值接近，不代表它们互相印证。** 我用 `query=<id>` 测得 1893 ms，同时本机对那一条 58 MB 日志的解码是 1870 ms，两者接近，我就把它当成「宿主成本 = 单条日志解码成本」的交叉验证写进了结论（还推了个 `32.5 ms/MB` 的系数）。实际上 1893 ms 是**整个候选集**的成本（同一次响应自己就写着 `fetched:23`），1870 ms 是**单条**的成本 —— 两个不同的量碰巧数值接近。
   - **更严重的是我漏做了一步**：真正的交叉验证要先用 `/list` 拿到**宿主实际折叠标题的那 16 条候选**，再只对这 16 条做本机解码。补做之后才看到正确结论：本机在 16 条语料上是 2746 ms、宿主 1632 ms，比值 **1.68**；在旧的 23 条语料上是 3521–3620 vs 2149，比值 **1.64–1.68** —— 两个语料上比值稳定，这才是站得住的交叉验证（本机成比例地偏慢，可用于相对排序，不可用于绝对预测）。
   - **口径陷阱**：磁盘上有 56 个日志 / 102.1 MB，但 `/list` 默认 `kind=main` 会排除 subagent 与部分归档会话，**实际候选只有 16 条 / 51.7 MB**。拿磁盘总量去比宿主成本，会得出约 3 倍的假差异，并进而误判「本机测量不可信」。**任何本机/宿主对比都必须先对齐候选集。**
   - 教训：交叉验证的两个数必须**先确认测的是同一个对象**，再比数值；相近只是必要条件的错觉，不是充分证据。

## 10. 复现方式

报告中的所有【真机】数字都可以重跑。宿主端口是动态分配的，脚本必须自己发现端点（支持 `DC_BASE` 显式指定；发现多个候选会报错要求显式指定，**绝不猜地址**）。

```bash
# 阶段 A：宿主恢复检查
node scripts/bench-real-host.mjs status

# 阶段 B-01：热态基线（10 次）
node scripts/bench-real-host.mjs series --n 10 --pageSize 50

# 阶段 B-04：pageSize 扫描
node scripts/bench-real-host.mjs sizes --pageSizes 1,5,10,25,50,100,200

# 阶段 C-01：并发分档（热态；冷态并发见下面的注意事项）
node scripts/bench-real-host.mjs concurrent --levels 1,2,4,8 --rounds 3 --pageSize 50
```

脚本的安全边界写在文件头：只发 `GET /status` 与 `GET /list`，结果一致性只比较 **sessionId 集合的 sha256 前 12 位指纹**，不输出标题文本、会话正文或 `cwd`。

**冷态样本必须用「零请求静默」取得**（这一点是整个 PERF-04 最容易做错的地方）：

1. 记下**最后一次真实请求**的时刻作为锚点；
2. **一个请求都不发**，连轻量探测也不发，静默 `titleCacheTtlMs + 60 s`（默认 360 s）；
3. 静默结束后做**唯一一次**测量；
4. 用**该次测量自身**的 `titles` 判定有效性：`cached==0 && fetched>0` 才算真冷，否则记 `cold=false` 并排除。

**不要**用 `query=<id>` 探测（会走搜索分支、把整个候选集标题烘热），也**不要**用 `page=N` 探测（探针那一条常比待测条目更早过期，且轮询本身不断重置时钟）。任何探测都会污染冷态，这一点由 TTL 语义决定，绕不过去。

**不要用「重启宿主」来制造冷态**——重启会把首查变成最坏情况（3.8–5.3 s）而污染对比；正确做法是等 TTL 自然过期。
