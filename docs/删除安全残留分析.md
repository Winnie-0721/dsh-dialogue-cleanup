## 4.1 运行状态检查与磁盘删除之间的竞态

### 触发条件

`deleteSession` 的步骤 1（`judgeRunning` 判 running）与步骤 3（`removeArtifacts` 真正 `rm`）
之间存在一个时间窗。窗口内如果该会话开始运行，检查结论就过期了：

```
t0  judgeRunning(snapshot) → running:false          ← 判定 idle，通过
t1  （另一个请求/用户在界面里开始这个会话）          ← 状态变了
t2  rm -rf <sessions>/<proj>/<id>                    ← 删掉一个正在运行的会话目录
```

窗口宽度 = t0 与 t2 之间的所有工作：读 live 集合、`detachLiveStore`、
`readPersistedSessionIds()`（一次 `sessionQuery.listSessions()`，**含磁盘 IO**）、
`removeArtifacts` 的 readdir + 逐目录 lstat + realpath + rm。
在 500 条会话的实测里，这段是**毫秒级到数十毫秒**，`listSessions` 在真实 54 MB
日志上可达数百毫秒（见 CHANGELOG 的冷路径取证）。窗口不是零。

### 可能后果

**数据丢失**：正在运行的会话，其磁盘工件被删除。运行中的 agent 随后写入会失败或
写到已被删除的路径；用户正在进行的对话上下文丢失。这是本插件最严重的可能后果，
因为它**不可逆**。

### 公开 API 调查结论（实测，非推测）

对 `D:\Software\DeepSeek Harness\resources\app.asar`（182 MB）逐字符串检索：

| 符号 | 命中 | 性质 |
|---|---|---|
| `deleteSession` | 17 | **ACP agent 协议**（`AGENT_METHODS.session_delete`），是 agent 侧能力，不是宿主的会话锁 |
| `SessionWriteLease` | 4 | **真实存在**：`SessionWriteLease.acquire(dir, id)` |
| `acquireLockHandleWin32` | 3 | Windows 命名信号量 `Local\dsh-session-lock-<sha256(realpath)>` |
| `releaseLockHandleWin32` | — | 释放：恢复计数并关闭句柄 |
| `SessionAlreadyOwnedError` | 3 | 已被占用时的错误；宿主把它翻成 `RemoteError("session/writer-held", …)` |
| `session/writer-held` | 2 | **只出现在 resume 失败路径**：`if (error.name === "SessionAlreadyOwnedError") return RemoteError("session/writer-held", …)` |
| `sessionLock` / `atomicDelete` / `removeSession` | 0 | 不存在 |

**结论：宿主的写锁是真实的、内核级的，但对插件不可达。**

`SessionWriteLease` 是 DSH 内部模块的实现细节（`var SessionWriteLease = class …`，
无 export 块、无 `ctx.*` 服务挂载）。它唯一对外可见的表现是 **resume 被占用时返回
`session/writer-held`** —— 那是一条*错误*，不是可调用的锁。宿主没有暴露
`ctx.sessionLock` / 租约 / 生命周期回调（`beforeDelete` 只命中 luckysheet 表格组件，
与会话无关）。

因此按任务书 §4.1.3：**不得声称竞态已被彻底消除**。

### 采取的策略（能实现的最保守）

1. **缩短窗口 + 删除前二次确认**：在 `removeArtifacts` 真正 `rm` 之前，用一个
   `beforeDelete` 回调再问一次运行态（`judgeRunning`）。第一次检查仍在最前面
   （早拒绝、省工作），第二次紧贴删除动作。窗口从「整个事务」缩到「单次探测 → rm」。
2. **二次确认失败即拒绝**：回调返回「running / 不可知」→ 该目录进 `skipped` 并带
   `reason`，删除结果为 partial，**不报完整成功**。
3. **可注入以便确定性测试**：`beforeDelete` 是 `removeArtifacts` 的选项，
   测试可以精确构造「第一次检查后、rm 前变 running」。
4. **不引入任何私有 API**：不碰 `fiber`、不 import 宿主内部模块、不调
   `SessionWriteLease`。二次确认只用已核验的公开面（`sessionController.list` + `agents.get`）。

### 残余风险（如实披露）

- 二次确认本身仍是「检查—使用」两步：Windows 信号量那类**真正的互斥**拿不到，
  所以 t1 仍可能落在「二次确认完成之后、`rm` 系统调用之前」这一微窗口内。
  该窗口是**单条语句级**（`await isRealPathInside` 之后立即 `await doRm`），
  比修复前小若干个数量级，但**不为零**。这是公开 API 下的硬上限。
- 要彻底消除，需要宿主暴露一个「删除会话」的原子入口（或把写锁暴露给插件）。
  宿主已有 `SessionWriteLease`，**建议上游把 `acquire` 挂到公开服务上** ——
  那之后本插件可以改成「先持锁再删」。

## 4.2 `sessions.list()` / 会话身份查询失败不得静默

### 触发条件与后果（逐条）

| 路径 | 原行为 | 后果 |
|---|---|---|
| `sessions.list()` 抛错 | `catch { }` → `liveIdsKnown=false` | 影响 `stillInLiveStore` 判定；**静默** |
| `sessions.list()` 返回非数组 | `for (const s of sessions.list() ?? [])` → 抛 TypeError | 被同一个 `catch` 吞掉 → 同上 |
| `sessions` 服务未注入 | `typeof sessions?.list === "function"` 为假 → `liveIdsKnown=false` | 同上 |
| `sessionQuery.listSessions()` 抛错 | `readPersistedSessionIds()` 返回 `null` | 守卫收紧为「不碰对偶拼写」→ **已是 fail-closed**，但**没有任何降级项上报** |

前三条影响的是「内存里还有没有这个会话」——它决定要不要摘工作区归属，
**不决定删不删磁盘**，所以不构成越界删除风险；但它是同类「静默降级」，
用户看到 `complete:true` 而实际有个判断没做成。

第四条已经 fail-closed（正确方向），但静默：用户无法知道「对偶拼写这次没删是因为
守卫不可用」，会误以为「我没有另一个拼写」。

### 采取的策略

- **`sessions.list()` 失败**：区分「服务缺失（能力缺失，正常）」与「调用抛错/返回非数组
  （真失败）」；后者进 `degradations`（step `readLiveIds`）。空数组是**正常结果**，
  与读取失败严格区分。
- **`readPersistedSessionIds()` 失败**：仍 fail-closed（不碰对偶拼写），
  但进 `degradations`（step `readPersistedIds`），并给出 reason，让用户知道
  「对偶拼写被保守跳过」的真正原因。
- 两者都**不影响**精确 id 的删除（那是安全的），只影响歧义候选与归属摘除。

## 4.3 项目目录符号链接 / junction 的可观测性

### 触发条件与后果

`removeArtifacts` 的循环开头是 `if (!proj.isDirectory()) continue;`。
Windows 上 `readdir` 对**任何**重解析点（`mklink /J`、`mklink /D`、文件符号链接）
都报 `isDirectory:false / isSymbolicLink:true`（实测确认）。于是：

- 安全方向是**对的**：链接不会被跟进删除，`rm -r` 不会越界。
- 但它是**静默**的：既不进 `skipped`，也不进 `failures`。如果某个会话的数据
  只存在于该链接指向处（用户把项目目录做成了链接，或用了目录联接），
  删除会返回 `complete:true` 而实际数据没删 —— **把「跳过了潜在数据」报成完整成功**。

### 采取的策略

- 显式识别重解析点（`proj.isSymbolicLink()` 或 `!proj.isDirectory()`），
  记入 `skipped` 并带 `reason: "project-dir-is-link"`，同时进 `degradations`
  （step `artifacts`，因为删除**没有完成**）。**不再静默**。
- 保持 `isRealPathInside()` 在**每次实际 `rm` 之前**执行（正向断言：内→true；
  反向断言：经父组件链接逃逸→false），防止未来重构移除该防线。

## 4.4 删除事务结果语义

已具备（上一轮整改）：`complete` / `partial` / `degradations` / `nothingDeleted` /
`failures` 五件套；ENOENT 与真实错误分离；`detachLive` / `detachWorkspaces` /
`clearRegistryRecords` / `announce` / `audit` 各自的降级项。

本轮补充：
- `skipped` 从「路径字符串数组」升级为**结构化 `skippedDetails`**
  （`{path, reason}`），使「为什么跳过」可诊断；保留 `skipped: string[]` 兼容既有契约与界面。
- 批量删除的 per-item `outcome` 已含 `complete/partial/noop/refused/blocked`，
  重试只需重跑 `outcome !== "ok"` 的条目。
- 面向用户的错误消息不再内嵌会话标题（标题可能含敏感内容）；失败清单只带
  步骤 + 路径 + 错误码。
