## 1. P0：删除状态一致性

### 1.1 完整删除流程（梳理结果）

`lib/service.js` 的 `deleteSession`，按副作用顺序：

| # | 步骤 | 输入 | 失败条件 | 失败后的**可观测性**（修复前 → 修复后） |
|---|---|---|---|---|
| 1 | id 校验 | `sessionId` | 正则不匹配 | `ok:false`（一直正确） |
| 2 | 单飞去重 | `sessionId` | — | 复用同一 Promise（一直正确） |
| 3 | 运行态判定 | 快照 + `agents` | 判定为 running | `refused`（一直正确） |
| 4 | 空闲 agent 守卫 | `probe.hasAgent` | 无公开停止入口 | `refused`（一直正确） |
| 5 | 读 live 集合 | `sessions.list()` | 抛错 → **静默** | 仍为静默（**已知残留**，见 §6） |
| 6 | 摘内存 live 条目 | `sessions` | 无入口 / 抛错 | `detach:"failed"` → 现进 `degradations` |
| 7 | 删磁盘工件 | root + 守卫 | readdir/rm 抛错 | **修复前：完全静默** → 现 `error`+`failures`+`degradations` |
| 8 | 删投影缓存 | 同上 | 同上 | 同上 |
| 9 | 摘工作区归属 | `registry` | list/detachSession 抛错 | **修复前：返回 `0`，与「没有工作区」无从区分** → 现结构化 `{removed,failures,error}` |
| 10 | 清注册表残留 | `registry` | 方法抛错 | 现有 `attempted/resolved` 对比 + `degradations` |
| 11 | 通知侧栏 | `ctx.emit` | emit 抛错 | `announced:false`；**区分能力缺失 vs 真失败** |
| 12 | 审计落盘 | `audit.record` | 写失败 | `value.audit.ok=false`；现进 `degradations` |

### 1.2 统一结果模型（修复后）

单条与批量现在共用同一套判定，**五种情形互相可判别**：

```js
value.complete        // 完整成功：所有破坏性步骤都完成
value.partial         // 至少一个破坏性步骤没完成（= degradations.length > 0）
value.degradations[]  // [{ step, reason, failures? }] 逐项降级明细
value.nothingDeleted  // 什么都没删到（幂等重删 / id 不存在）
value.failures[]      // 磁盘层逐路径失败清单
```

批量（`lib/index.js`）在同名字段基础上返回
`{ total, ok, fail, complete, degraded, partial, noop, degradations, files, outcomes }`。

### 1.3 复现 → 修复 → 复跑（P0-1）

**复现**（`_repro-false-ok.mjs`，已随整改删除）：把 `<DSH_HOME>/sessions` 做成一个**文件**，
使 `readdir` 抛 `ENOTDIR`；同时让 live 摘除成功：

```
HTTP 层面：ok = true
value.detach = detached   value.files = 0   value.partial = false
sessions 仍然是那个文件（磁盘删除其实没成功）= true
★ 缺陷确认：磁盘删除失败被吞掉，事务报 ok:true 且 partial:false
```

**根因**：`artifacts.js` 的 `catch { return {count:0,...} }` 把**所有** `readdir` 失败
都当成「根不存在，没什么可删」。而 `readdir` 失败的成因远不止不存在：
`ENOTDIR` / `EACCES` / `EPERM` / `EBUSY` / `EMFILE` / `EIO` —— 它们都意味着「**没能删**」，
却与「这个会话没有磁盘工件」返回了**完全相同的结构**。

**修复**：三态分明 —— `ENOENT`→`rootPresent:false, error:null`（正常收尾）；
其它 → `error` 如实带上、逐路径 `failures` 记录；`rm` 失败不再直抛而是逐目录记录后继续。

**复跑**：同脚本现在输出 `value.partial = true` → 「未复现」。

### 1.4 复现 → 修复 → 复跑（P0-2，数据丢失级）

**复现**（`_repro-alt-spelling.mjs`）：磁盘上同时存在 `p/<uuid>` 与 `q/session-<uuid>`，
两者都是真实会话，live 集合为空：

```
A: ok = true files = 2 skipped = []
   对偶目录 session-<uuid> 仍在 = false
   → ★ P0-2 复现：对偶拼写被一并删除（它是另一个真实会话）

B2: 重试（兄弟已不 live）→ files = 1 skipped = []
   兄弟目录已消失 = true
   → ★ P0-2b 复现：同一请求重试后删掉了先前被正确保护的另一个会话
```

**根因**：`isKnownSession` 只查 **live 集合 + `agents.get()`**。于是
「已持久化但当前不 live」的会话（用户关掉的会话、宿主重启后的会话）全部被判为
「不存在」，继而被当成「我这个 id 的另一种拼写」而 `rm -rf`。
注释承诺的是「确认它不是另一个已知会话」，实现只确认了「它不是另一个**在线**会话」。

**修复**：把**持久语料**（`sessionQuery.listSessions()`）纳入判据 —— 那才是
「有哪些会话真实存在」的权威全量来源。并确立一条原则：
**无法证明它不是另一个会话，就不能删它**（守卫不可用时传 `null`，
`removeArtifacts` 随即跳过对偶拼写）。

> 这里我第一次修得不对：仍然构造了一个「永远返回函数」的守卫，
> 于是 `isKnownSession === null` 那条保守分支**永远进不去**，复跑后缺陷照旧。
> 是复跑发现的，不是推理发现的 —— 记录在此以免后人重犯。

**复跑**：A → `files = 1`、对偶目录仍在；B2 → 兄弟目录仍在。

## 2. P1：运行状态与内部 API

1. **`runningProbeTtlMs` 使用范围**：该缓存**实例级**，且可能来自**上一次删除请求**。
   列表用它无害（只影响界面 `deletable` 标记）；删除用它有实质风险。
2. **删除前重新验证（已修）**：`deleteSession` 默认走新的 `freshRunningSnapshot()`
   （绕过 TTL）；批量由 HTTP 层在整批开始前取**一份新鲜快照**、批内复用 ——
   既满足「删除前重新验证」，又保住 O(1) 次探测（实测批量 50 条仍只探测 1 次）。
3. **竞态**：状态检查与磁盘删除之间仍有理论窗口（检查后、删除前会话开始运行）。
   属**已知残留**，见 §6 —— README/配置里已如实声明该折衷，未降低检查强度。
4. **内部字段访问**：`detachLiveStore` 的「内部 store Map」分支是本插件**唯一**
   触碰宿主私有结构的地方，已集中在这一个函数内并有三态返回值。
5. **启动时能力检测**：`capabilities()` 覆盖必需接口（`removeArtifacts:true` 为常量，
   因为磁盘层不依赖宿主服务）；`detachLiveEntry` 按「store 可达 **且** entry 带官方
   `detach`」判定，避免旧探针「恒为 true 却与事实不符」的误导。
6. **不使用未经验证的私有 API 停 Agent**：`stopIdleAgent` 只认公开入口，
   探不到就**如实返回 false** 由上层拒绝；`publicStopIdleAgent` 恒为 `false`，
   真实 DSH 只读检查确认它如实报告（见 §4）。**未使用** `fiber._unload()`。

## 3. P1：文件系统安全

### 3.1 越界删除（P0-3，本轮最严重）

`isInside()` 是**纯字符串前缀**比较，不解析链接。若 root 下某个**父组件**
（项目目录）是指向 root 之外的 junction/符号链接：

- `join(root, proj, id)` 字符串仍以 root 开头 → `isInside` **通过**；
- `lstat(root/proj/id)` 跟随父组件链接，报告「普通目录、非符号链接」→ 符号链接守卫**也通过**；
- `rm(recursive)` 删掉 root 之外的**真实目录**。

**复现**（竞态版，`_repro-junction-race.mjs`）：

```
换入 junction 成功 = true
removeArtifacts 返回 count = 201  error = null
root 外的重要文件幸存 = false
★ P0-1（竞态）复现：经父组件 junction 逃出 root 并删除外部目录
```

**修复**：新增 `isRealPathInside()` —— 用 `realpath()` 解析**真实路径**后
再与**解析后的 root** 做包含校验；任何一步解析失败即返回 `false`（宁可不删）。
在 `removeArtifacts` 与 `removeProjectionCache` 的**每个 `rm` 之前**强制校验。

**复跑**：

```
removeArtifacts 返回 count = 200  error = .../zzz-victim/s1 :: 真实路径落在会话根之外（疑似符号链接/junction 逃逸），已拒绝删除
root 外的重要文件幸存 = true
```

### 3.2 其余文件系统检查

| 项 | 结论 |
|---|---|
| `..` / `\` / 分隔符 / 兄弟前缀（`sessions` vs `sessionsX`） | 实测均正确拒绝 |
| 大小写折叠（Windows） | 正确 |
| UNC `\\srv\share` 与 `\\?\` 前缀 | 实测无逃逸 |
| 尾随点/空格别名（Windows） | 返回 false —— **保守的方向**（漏删而非误删） |
| 目录符号链接 / junction（候选本身） | `lstat` 拦下并记入 `skipped` |
| 目录符号链接（作为项目目录） | Windows 上 `readdir` 报 `isDirectory:false`，跳过且**不记 `skipped`**（**已知残留**，见 §6） |
| 同一 root 下多项目、同名候选目录 | 实测不会误删（守卫 + 真实路径校验双重） |
| 磁盘删除失败能否到达 HTTP/UI/审计 | **修复后可以**：`error`/`failures`/`degradations` 三层贯通 |
| 权限不足 / 文件占用 / 目录不存在 | 分别由注入式测试 + ENOENT/ENOTDIR 真实用例覆盖（§1.5） |

## 6. 未解决风险与已知残留

如实列出，未粉饰：

1. **状态检查与磁盘删除之间仍有理论竞态**。检查通过后、`rm` 之前会话开始运行，
   仍会被删。窗口极小（同进程内相邻两条语句），但**存在**。
   未用加锁/二次校验彻底消除，因为宿主未提供「持有会话锁」的公开能力。
2. **`detachLiveStore` 分支①不自证**：公开 `detach/release/close` 存在时，
   代码只凭「可调用」就返回 `"detached"`，不校验结果；若该方法是 `async`，
   其 rejection 会成为 unhandledRejection。**当前运行时无公开 detach**
   （`capabilities.publicStopIdleAgent=false`），故属**前瞻性缺陷**：
   一旦宿主新增公开停止入口，这段需要补「调用后校验 + await」。
3. **`sessions.list()` 读失败仍为静默**（§1.1 第 5 步）：`liveIdsKnown=false` 后
   按「不可知」继续，不产生降级项。影响面小（只影响 `keptWorkspaceMembership`
   的判定方向），但是同类「静默降级」，未在本轮修。
4. **目录符号链接作为项目目录时不记 `skipped`**：Windows `readdir` 把它报成
   `isDirectory:false`，循环开头直接跳过，因此 `skipped` 为空 ——
   若会话数据只存在于该链接指向处，会表现为「静默成功但没删到」。未修（会改变
   现有跳过语义），如实记录。
5. **审计日志增长偏快**：实测 38 行 / 33.8 KB ≈ **910 B/行**，因为每行内嵌了
   完整结果对象（含 `removedPaths`、`runtime`）。未加轮转或字段裁剪。
6. **未做**：真实宿主破坏性集成测试、真实进程 kill/重启测试、Linux 实机测试
   （路径用例在 POSIX 分支写了但本机只跑 Windows）。
7. **对偶拼写仍然结构性有歧义**：修复后守卫依据「持久语料里是否存在该 id」，
   这能回答「它是不是一个真实会话」，但**不能**回答「它是不是**我**那个会话」
   （raw 调用只传字符串 id，没有 cwd）。在本机实测的 57 个会话中，
   目录名与 header id 严格 1:1、两种拼写是**不同会话**，因此当前策略
   （语料里存在即拒绝删除对偶拼写）是安全的；但若某宿主真的用两种拼写指向
   同一会话，本策略会**漏删**而非误删 —— 方向正确。
8. **`removeProjectionCache` 的 `rootPresent` 恒为 `true`**：它按精确文件名删除、
   不列举 root，故无法判断 root 是否存在。字段语义已注明，未伪造探测。
