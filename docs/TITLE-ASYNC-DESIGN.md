# 标题异步化设计（TITLE-ASYNC）

> 状态：**设计稿 + 模拟宿主原型，未改生产代码**。
> 本文不声称已在真实 DSH 上验证；真实宿主验收未做（任务书 §任务三 明确「没有宿主证据时标注未验证」）。

## 1. 为什么不是「随便加个 setTimeout」

先说清楚被否掉的三个直觉方案，以及它们为什么在这里都不成立。

### 1.1 先把 await 挪到 setTimeout 里 —— 无效

当前 `/list` 的耗时结构是：

```
listSessions()
  ├─ sessionQuery.listSessions()      // 宿主索引，便宜
  ├─ sessionController.list()          // 运行态，便宜
  ├─ 过滤/排序/分页
  └─ await ensureTitles(当前页)        // ← 慢在这：宿主解压整份会话日志
```

`ensureTitles` 的成本在**宿主侧**（`readTitleSnapshots` 要解压 `session.v4.jsonl.zstd` 再 `findLast(type==="session/title")`），不是在本侧的排队。
把 `await` 包进 `setTimeout(…, 0)` 只是换了个地方等，**总时长不变**，首屏照旧被阻塞。
真正的异步化必须改**契约**：先返回「标题待定」的列表，再在后台补齐、并有可观测的完成信号。

### 1.2 用固定延时「等标题就到」 —— 把正确性换成了运气

`setTimeout(完成回调, 300)` 这类写法有三处硬伤：

- **不可判定**：到点了也不知道标题是「还没来」还是「永远不会来」，只能猜。
- **不可取消**：期间会话被删掉，回调照跑，容易写出幽灵行。
- **无界陈旧**：慢请求（实测冷态 763 ms）会稳定超过任何固定延时，于是「有时有标题、有时没有」，表现为随机闪烁而不是可解释的状态。

### 1.3 降 `titleLimit` / 加并发 —— 已知无效

PERF-03 已实测：并发 4/8 反而慢 22%/36%（`titleFetchConcurrency` 保持 8 最优），且标题成本由日志字节量决定，降条数只是把成本挪给下一页。
**结论**：异步化是唯一不动正确性、又能把首屏从 763 ms 拉到热态量级的路径。

## 2. 状态机（本设计的核心）

### 2.1 返回契约

`/list` 增加一个对象，不改变既有字段语义（`items[].title` 仍可为 `null`）：

```jsonc
{
  "items": [ { "sessionId": "…", "title": null,  "titleState": "pending" }, … ],
  "titles": {
    "token": 42,              // 单调递增，每次 /list 自增
    "state": "pending",       // pending | partial | complete | failed
    "pending": 16,            // 尚在读取的条数
    "ready": 0,               // 已填好
    "empty": 0,               // 宿主确认「没有标题」（≠ 读取失败）
    "unreadable": 0,          // 读取失败/超时
    "ms": 0                   // 本阶段已耗时
  }
}
```

关键区分：**`empty` 与 `unreadable` 必须分开**。
前者是「这个会话确实没起过标题」，界面显示占位文案即可；后者是「没读到」，界面应显示「重试」入口。
把它们混成一个 `null` 是本插件现在最大的可观测性缺口（列表里分不清「没标题」和「读取失败」）。

### 2.2 单条标题的状态

| 状态 | 含义 | 界面 |
|---|---|---|
| `pending` | 已发起、未出结果 | 骨架/占位，**不得**显示空串 |
| `ready` | 有标题 | 正常显示 |
| `empty` | 宿主确认无标题 | 固定占位（如「未命名会话」） |
| `unreadable` | 读失败/超时 | 占位 + 重试入口 |

### 2.3 两阶段刷新

```
请求 A：/list
  token=42, state=pending, items 带 titleState=pending
  → 立即返回（目标 P95 ≤ 热态 * 1.2）

后台：ensureTitles(当前页)  ← 复用现有单飞，不新增并发
  逐条结果回来 → 写 titleCache，并标记该 token 的完成度
  → 当 token 仍是最新时，客户端下一次轮询 /list 拿到补齐结果
```

「补齐结果怎么送达客户端」有两个选项，本设计**不替产品做决定**，只列约束：

- **A. 客户端轮询**（改动最小）：前端在收到 `state!=complete` 时按 300/600/1200 ms 退避重问 `/list`（带 `token`），直到 `complete|failed` 或超时上限 5 s。缺点：多几次往返。
- **B. 推送**（体验最好）：宿主侧 `ctx.emit` 推一条 `dialogue-cleanup/titles-ready`，前端收到后重拉。缺点：需要确认客户端能订阅插件自定义事件（**未验证**）。

> 无论 A 还是 B，都必须带 `token` 做栅栏：晚到的旧 token 响应不得覆盖新结果。

## 3. 竞态与失效（设计必须回答的六个问题）

### 3.1 增量填充 / 首屏状态

首屏**不等待**任何标题。`items` 一次性给全（该页所有行），标题逐条填。
即「行先齐、标题后到」，而不是「分批出行」——分批出行会让列表高度跳动，体验更差。

### 3.2 乱序结果

每个标题结果绑定 `(sessionId, token)`。
写回条件是**双重比对**：

```
if (token < state.latestToken) 丢弃;          // 整批过期
if (epochOf(sessionId) !== result.epoch) 丢弃; // 该行已被删/被改
```

绝不整批覆盖：结果按 `sessionId` 逐条合并。这样即使两次 `/list` 交错，也不会出现「新列表被旧标题盖回去」。

### 3.3 陈旧与新鲜度

标题本身没有 schema 级水位（详见 `docs/PERF-05-PROJECTION-CACHE-REPORT.md`：`asOfSeq` 是折叠水位、宿主 `stat()` 不透出 `eventCount`）。
因此本设计的**新鲜度只依赖 `token`**，即「同一次请求内不重复读、跨请求不交叉写」，**不声称能判断宿主侧标题是否落后于日志**。
这是有意的范围收敛：异步化解决的是「首屏等待」，不是「标题是否最新」。

### 3.4 读取过程中会话被删除

删除时该会话 `epoch += 1`（`deleteSession` 内递增，随 `titleCache.delete(id)` 一起做）。
迟到的标题结果 epoch 不匹配 → 丢弃，并且**不得重新 `titleCache.set`**。

> 现状（1.1.2）：`service.js` 删除时 `titleCache.delete(id)`，但迟到结果仍会 `titleCache.set` 回去。
> 实测影响：不产生幽灵行（列表 corpus 已不含该 id），只在极端时序下让缓存多一条无用条目。
> 异步化后这条从「无害」升级为「必须处理」，因为前端会按 token 合并结果。

### 3.5 读取失败

- 单条失败 → `unreadable`，保留该行，记 `failedIds`。
- 整批失败（RPC 抛错/超时）→ `state=failed`，**不得停在 `pending`**（否则前端会无限退避）。
- 失败重试：下一次 `/list` 只对 `failedIds` 重试，并做上限（同一 id 连续失败 3 次后进入 60 s 冷却），避免每轮都把失败成本重付一遍。

### 3.6 可观测量

每次响应必须带 `titles.{token,state,pending,ready,empty,unreadable,ms}`，**不得记标题正文**（审计与日志口径沿用现有脱敏规则）。

## 4. 验收标准（可测）

| # | 标准 | 测法 |
|---|---|---|
| A1 | 首屏不再被标题阻塞 | 假宿主把 `readTitleSnapshots` 阻塞 800 ms，`/list` 必须在 < 100 ms 返回且 `items` 齐全 |
| A2 | 首屏 P95 不超过热态 1.2× | 真实宿主只读基准（`scripts/bench-real-host.mjs`）对比异步前后 |
| A3 | 每条最终必有终态 | 逐条断言 `titleState ∈ {ready, empty, unreadable}`，**禁止永久 pending** |
| A4 | 迟到的旧 token 结果不得覆盖新 token | 交错两次请求，断言最终标题来自较新的 token |
| A5 | 删除期间的迟到结果不得复活 | 删除后释放标题闸门，断言该 id 不出现在任何响应里、`titleCache` 无条目 |
| A6 | 失败必须可见 | 让 `readTitleSnapshots` 抛错，断言 `state=failed` 且 `unreadable>0` |
| A7 | `empty` 与 `unreadable` 可区分 | 一个会话无标题、一个会话读失败，断言两个计数各自为 1 |
| A8 | 既有语义零回归 | 搜索/过滤/排序/分页/`canDelete` 全部沿用现有测试 |

A1/A4/A5/A6/A7 已在**模拟宿主**下用原型验证（见 `test/title-async-prototype.test.mjs`，标注「原型」）。
A2 需要真实宿主，**未做**；A3/A8 属于实现后的回归项，本轮不实现生产代码故未做。

## 5. 风险与未决

1. **客户端契约变更**：`/list` 新增字段须保持向后兼容（旧版 `client.js` 忽略即可），但「按 token 轮询」需要客户端配合 —— 客户端与宿主同包发布，需一次同步升级。
2. **推送通道未验证**：方案 B 依赖插件能向客户端推自定义事件；本轮**没有**验证这条通道是否存在，故默认走方案 A。
3. **根因未解决**：异步化只是把 763 ms 从「首屏」挪到「后台」，总成本不变。真正的解法仍是宿主提供标题索引（PERF-05 已向上游提出 API 需求）。
4. **标题新鲜度仍未解决**：本设计不声称标题一定最新；若将来需要「标题必须最新」，必须等宿主的稳定水位 API。
5. **多次往返**：方案 A 在大库上会带来额外 2–4 次 `/list`，需在真实宿主上量一次额外 CPU 与审计噪声（**未测**）。
