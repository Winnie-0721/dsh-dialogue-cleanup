## A-01 查询调用链（以当前代码为准）

### 客户端（`client.js`）

| 阶段 | 位置 | 输入 | 输出 | I/O |
|---|---|---|---|---|
| 触发 | `client.js:1918` `React.useEffect` | `params`（query/project/archived/kind/sort/page/pageSize/running）+ `reloadTick` | — | 否 |
| 请求 | `client.js:1801` `fetchList(request)` → `GET/POST {BASE}/list` | 同上 | JSON body | **网络** |
| 取消 | `client.js:1938` 闭包 `cancelled` | — | 旧响应被丢弃 | 否 |
| 渲染 | `client.js:1935` `setState({status:"ready", value})` | `body.value` | 表格行 | 否 |

**实测结论：客户端只有一处 `fetchList` 调用点，且带 `cancelled` 守卫。**
`useEffect` 依赖是 `[params, reloadTick]` —— `params` 是对象，若上游每次渲染都新建
对象会重复触发；这一点需在基准里用「请求计数」验证，不能靠读代码断言。

### 服务端（`lib/http.js` → `lib/service.js`）

```
HTTP /list
  └─ service.listSessions(request)          lib/service.js:1110
       ├─ ① Promise.all 并行：
       │     ├─ sessionQuery.listSessions()        【I/O：读持久语料，含读盘】
       │     └─ sessionController.list({}, undefined) 【I/O：宿主 RPC，实测约 100 ms 底噪】
       ├─ ② 合并成 rows（Map）
       ├─ ③ registry.list()                       【同步，可选增强】
       ├─ ④ readArchivedSessionIds(ctx)           【I/O：读 workspace 存储域】
       ├─ ⑤ 结构性过滤（project/running/kind/archived）—— 不依赖标题
       ├─ ⑥ 排序（ISO 字符串字典序，非 localeCompare）
       ├─ ⑦ ensureTitles(items, titleSearchLimit)  ← 仅当 query !== ""
       ├─ ⑧ 关键词过滤（id / title / cwd / workspaceTitle）
       ├─ ⑨ 分页 slice
       ├─ ⑩ ensureTitles(slice, titleLimit)        ← 无 query 时这是唯一一趟
       ├─ ⑪ deletable/blockedReason 判定
       └─ ⑫ 返回 { total, page, items, projects, sources, archived, kind, titles, tookMs }
```

### 各阶段 I/O 属性

| 阶段 | I/O | 可否并行 | 备注 |
|---|---|---|---|
| `sessionQuery.listSessions()` | **是**（读盘） | 已与下一项并行 | 语料全量 |
| `sessionController.list()` | **是**（RPC） | 已与上一项并行 | 摘要 running/blank/updatedAt |
| `readArchivedSessionIds` | **是**（存储域） | 未并行（在第 ③ 步之后同步取） | |
| `readTitleSnapshots(ids)` | **是（最贵）** | 分片并发（`titleFetchConcurrency`） | 每条需解压整份会话日志 |
| 过滤/排序/分页 | 否（纯 CPU） | — | 实测 1000 行约 2 ms |

### 标题读取为何是最可疑的一环

- 磁盘上只有 `session.v4.jsonl.zstd`，**没有独立标题索引**（历史取证）；
- 宿主 `foldSessionTitle` 是 `events.findLast(type === "session/title")`，
  必须解压整份日志才能拿到标题；
- 历史实测：**约 65 ms/条**（小日志）；54 MB 真实日志上约 350 ms/条；
- `readTitleSnapshots` 内部**串行**，本插件只能靠 `titleFetchConcurrency` 分片并行。

**默认预算**：`titleLimit=100`、`titleSearchLimit=40`、`titleFetchConcurrency=8`。
即首屏 50 行、冷缓存 → 50 条标题，按 65 ms/条、8 并发 ≈ 50/8×65 ≈ **406 ms**；
若按 350 ms/条则 ≈ **2.2 s** —— 与「约 2000 ms」的现象量级吻合。
**但这是推算，不是测量。阶段 A-03 必须用实测确认。**

### 首次 vs 后续的差异来源（待验证假设）

| 假设 | 机制 | 如何证伪 |
|---|---|---|
| H1 标题缓存冷 | 首次全部 miss，后续命中 `titleCache`（TTL 300 s） | 看 `titles.cached/fetched` 与 `titlesMs` |
| H2 宿主语料冷 | `sessionQuery.listSessions()` 首次需读盘/建索引 | 看 `sessionsMs` |
| H3 宿主摘要冷 | `sessionController.list()` 首次 RPC 建连 | 看 `runningStateMs` |
| H4 模块/进程冷启动 | 首次请求触发懒加载 | 看「服务启动后第 0 次 vs 第 1 次」 |
| H5 客户端重复请求 | `params` 每次新建 → `useEffect` 重复触发 | 数请求次数 |

## A-02 阶段耗时指标（实现说明）

在 `listSessions` 内用 **`performance.now()`**（单调时钟，不受系统时间跳变影响）
采集以下分段，每请求**一条**结构化摘要：

| 字段 | 含义 |
|---|---|
| `totalMs` | 服务端请求总耗时 |
| `sessionsMs` | `sessionQuery.listSessions()` 耗时 |
| `runningStateMs` | `sessionController.list()` 耗时 |
| `titlesMs` | 两趟 `ensureTitles` 累计耗时 |
| `filterSortPageMs` | 过滤 + 排序 + 分页 |
| `serializeMs` | 响应对象构建（`out` 映射 + 计数） |
| `titlesRequested` / `CacheHit` / `CacheMiss` / `Fetched` | 标题成本明细 |
| `resultCount` / `sessionCount` | 返回条数 / 候选条数 |
| `reqId` | 关联 ID（同一次查询的分段可对齐） |

**隐私约束**：只记计数与耗时，**不记**标题文本、会话正文、`cwd` 路径。

**开关**：默认每请求一条 `debug` 级摘要；`config.perfLog === "verbose"` 时才额外输出
每个标题分片的耗时。指标计算不改变任何返回值与异常传播。

## A-03 基准（实测，本机 Windows / Node v24.21.0 / `1a8920a`）

> **重要说明（不得混淆）**：以下数据来自 **fake I/O 基准**（`scripts/bench-list.mjs`），
> 注入固定延迟模拟宿主耗时特征。它测的是**服务端逻辑开销与复用效率**，
> **不是**真实 DSH 宿主上的绝对延迟。真实宿主数据见 §A-04。

运行：`node scripts/bench-list.mjs --sessions=N --title-ms=65 --concurrency=8 --rounds=N`

### 阶段拆解（冷缓存首查，50 / 200 / 500 条候选）

| 候选数 | totalMs | sessions | runningState | **titles** | filterSort | serialize |
|---|---|---|---|---|---|---|
| 50 | 503 | 21 (4%) | 104 (21%) | **397 (79%)** | 0 | 0 |
| 200 | 587 | 21 (4%) | 114 (19%) | **468 (80%)** | 0 | 0 |
| 500 | 588 | 21 (4%) | 115 (20%) | **470 (80%)** | 0 | 0 |

**结论：标题读取是绝对瓶颈（79–80%）。** 过滤/排序/序列化合计 < 1%
（1000 行约 2 ms，与本表一致），因此**不做**相关重构。

### 冷 / 热对比（50 条）

| 指标 | 首查 | 第二查 | 热 P50 | 热 P95 | 热 max |
|---|---|---|---|---|---|
| totalMs | 511 | 109 | 109 | 113 | 114 |

首次 ≈ 5× 热查。热查的 109 ms ≈ `runningState`（宿主 RPC 100 ms）+ 常驻开销，
即**热路径已压到宿主底噪**，没有服务端优化空间。

### 「首次打开插件」vs「每次冷查询」

| 场景 | P50 | P95 | max |
|---|---|---|---|
| 每次全新实例（= 首次打开插件） | 504 | 507 | 509 |
| 同实例热查 | 109 | 111 | 111 |

两者**没有额外差异**——不存在「只有第一次特别慢」的初始化惩罚。
冷查询慢是**每次标题缓存清空都慢**，与插件打开次数无关。

### 并发的标题 I/O（可量化的浪费）

| 场景 | 耗时 | corpus 调用 | summary 调用 | title 调用 | 读取标题数 |
|---|---|---|---|---|---|
| 单请求（200 条候选，取 50 标题） | — | 1 | 1 | 8 | **50** |
| 8 并发（同一实例，冷缓存） | 119 ms | 8 | 8 | 64 | **400** |

**8 个并发请求读了 400 条标题，而它们要的是同一批 50 条 —— 8× 完全重复，零复用。**
这违反了任务书 §4-B-01「检查一次请求中是否重复调用…对同一次请求内可复用的数据
进行局部复用」，但这里是**跨请求**的重复：每个请求独立发起同一批标题读取。

### 并发数对标题阶段的影响（500 条候选，测的是分片并行的有效性）

| titleFetchConcurrency | totalMs | titlesMs | titles 占比 |
|---|---|---|---|
| 4 | 971 | 855 | 88% |
| 8（默认） | 586 | 466 | 80% |
| 16 | 369 | 262 | 71% |

**并发是有效杠杆**，但**不能盲目调高**：`titleFetchConcurrency` 是本插件唯一会造成
可观 I/O 并发的参数，配置注释已明确「宿主吃紧时调回 4 甚至 1」。
因此**只提默认值不是安全的通用解**——需配合去重，否则只是把争用推给宿主。

### 异常降级（不得静默当成「没有会话」）

| 场景 | 结果 |
|---|---|
| 语料抛错 | `sources.corpus=none`，落到 `sessionController.list`，仍返回 10 行 |
| 摘要抛错 | `sources.summary=none`，语料仍在，仍返回 10 行 |
| 标题抛错 | 仍返回 10 行，`titles.failed=10`、`fetched=0`（如实上报，非静默无标题） |

三条都**没有抛错穿透**，且失败来源在 `sources` / `titles.failed` 里可判别。

## A-04 真实 DSH 宿主（只读）

> 只调用 `/status`、`/list`，**不删任何真实会话**。

### 结果：**未能取得有效基线，并暴露一起由本次改动引发的事故**

首次调用 `/list?pageSize=50` 即返回 500：

```json
{ "ok": false, "error": { "code": "internal", "message": "part is not iterable" } }
```

**根因（已定位，是本次改动造成的）**：

本仓库的插件是通过**符号链接**挂载到宿主 profile 的：

```
C:\Users\28062\.dsh\profiles\desktop\node_modules\dsh-dialogue-cleanup
  → E:\Code\dsh-dialogue-cleanup          （LinkType: SymbolicLink）
```

也就是说**宿主的 `require` 直接读我当前的工作树**。我在实现 single-flight 时连续编辑了
`lib/service.js` 两次：先把分片的返回值从「数组」改成「`{collected, failedIds}`」，
再改消费端。宿主恰好在这两次编辑之间触发了一次请求，于是加载到
「生产者已返回对象 / 消费者仍在 `for (const result of part)`」的**中间态**，
抛出 `part is not iterable` 并**常驻内存**（Node 模块缓存不会自己失效）。

**当前磁盘代码是正确的**（有 `Array.isArray(part)` 守卫，本地直测 20 行/20 标题正常），
但宿主内存里仍是那份中间态模块，**必须重启 DSH 进程才能恢复**。

**这起事故的四点教训（已写入交付说明）**：

1. **符号链接挂载意味着「编辑即上线」**。本仓库跑在活宿主上时，任何中间保存都可能被
   下一次请求加载。改 `lib/` 期间应当先停用插件、或改完一次性 `node --check` + 自测后再让它被请求。
2. **本次改动本可以不破坏兼容**：若先给消费端加守卫、后改生产者，任何中间态都安全。
   顺序错了，风险就变成了生产事故。
3. **本地测试全绿并不能保证宿主可用**——248 条测试跑的是「加载完成的模块」，
   永远看不到「编辑中途的模块」。这是测试覆盖的固有盲区。
4. **必须重启宿主验证**，不能只看磁盘代码。

**A-04 状态：未取得真实宿主基线（阻塞于需要重启 DSH）。**
真实宿主上的绝对延迟、以及「约 2000 ms 是否能在真实数据上复现」——**均未验证**。
本报告 §A-03 的数字**只代表 fake I/O 下的服务端逻辑开销**，不得当作真实环境实测。

## 优化前后对照

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 冷查询 totalMs（50 条，65ms/条） | 503 | 516 | **无实质变化**（±噪声） |
| 冷查询 totalMs（500 条） | 588 | 568 | 无实质变化 |
| 热查询 P50（50 条） | 109 | 109 | 无退化 |
| 热查询 P95 | 111 | 113 | 无实质退化 |
| **8 并发读取标题数** | **400** | **50** | **−87.5%（8×→1×）** |
| **8 并发标题 RPC 次数** | **64** | **8** | **−87.5%** |
| 结果条数 / 排序 / 分页 | — | 与基线逐字段一致 | 无变化 |
| 删除安全（deletable/blockedReason） | — | 与基线一致 | 无变化 |

### 必须如实说明的三点

1. **单次冷查询没有变快。** single-flight 只合并**并发**的重复读取；
   一个请求自己要读 50 条标题，这 50 条该读还得读。
   **「首次查询 P95 降 30%」这个目标在单请求场景下没有达成**。
2. **真正的瓶颈是宿主 I/O，不是本插件逻辑。** 标题占 79–81%，慢的原因是宿主必须
   解压整份会话日志才能拿到标题（磁盘上没有独立标题索引）。本插件已用
   `titleFetchConcurrency` 把「50×65ms 串行」压成「50/8×65ms」；调到 16 可到 262ms，
   **但那是把 I/O 压力推给宿主**，不能作为默认值强行提高。
3. **唯一可控且无副作用的改善是消除重复。** 8 并发读 400 条、实需 50 条是**纯浪费**，
   已消除（−87.5%）。真实场景中并发查询确实会发生（多标签页、重渲染叠加手动刷新）。

### 若目标是「单次冷查询更快」，剩余可行路径（需维护者决策）

| 方案 | 预期收益 | 代价 | 建议 |
|---|---|---|---|
| `titleFetchConcurrency` 默认 8→16 | titles 397→262ms（−34%） | 宿主瞬时并发翻倍；配置注释已警告「吃紧时调回 4」 | **交维护者按宿主能力决定**，不擅自改默认 |
| 降低 `titleLimit`（首屏标题数） | 线性下降 | **减少标题显示** → 违反「不改语义」 | 不做 |
| 让宿主提供标题索引 | 根本解决 | 上游改动 | 作为上游建议 |
| 首屏先渲染无标题、标题异步补 | 感知延迟骤降 | 需客户端两段渲染 + 契约改动 | 超出「最小改动」范围 |

## 环境限制与未解决项

1. **未在真实 DSH 宿主上测出绝对延迟。** 本报告数字全部来自 fake I/O 基准
   （注入 65 ms/条，历史实测的小日志值）。真实 54 MB 日志可达 350 ms/条，
   若如此则 50 条按 8 并发 ≈ 2.2 s，与「约 2000 ms」现象量级吻合——
   **但这是推算，不是测量**。
2. **客户端渲染耗时未测**：接口自带 `tookMs`，浏览器侧渲染无法在本环境稳定测量。
   若客户端总耗时显著高于 `tookMs`，需另做客户端 profile。
3. **`titleInFlight` 无容量上限**：只活一次读取周期（读完即删）。未加上限是因为
   上限本身会引入「超限就重复读」的回退路径，反而削弱去重。如需上限，先测真实并发峰值。
4. **未改任何默认配置**：`titleFetchConcurrency` 仍是 8、`titleLimit` 仍是 100、
   `titleSearchLimit` 仍是 40 —— 按「不擅自用 TTL/预算掩盖慢查询」的要求保持原样。
